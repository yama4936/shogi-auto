## 特定できた性能問題

1. `sorted(board.legal_moves)` がPythonのlength hintを使い、ライブラリの`__len__`で全合法手を数えた後、もう一度全列挙していた。
2. 深さ0の評価直前にも全合法手をソートしていた。終局判定には「合法手が1つあるか」で十分で、末端ごとに余計な分岐数ぶんの処理をしていた。
3. 反復深化の各深さで根の合法手を再生成していた。
4. 初回の1手先すら完了しないと、途中で評価できた根の手を全て捨て、並び順だけの初期fallbackへ戻っていた。

旧版のCPU 128局でも、局あたり平均完成深さは約0.096だった。
完成深さは非負整数なので、こうした平均値はほとんどの手番で初回反復が完成せず、旧版では未評価fallbackが返っていたことを示す。
単に「学習モデルが弱い」とだけ判断できる評価条件ではなかった。

1手先・27合法手のあるCPU診断局面では、約0.064秒のうち約0.060秒が`ordered_moves`に集中し、
leaf 27件に対し合法性チェックが1500件以上走っていた。

## 修正と同値性

- 合法手をgeneratorとしてソートし、件数確認による二重列挙を避ける。
- 深さ0では最初の合法手だけを確認し、無ければ従来と同じ詰み・合法手なしの評価を返す。
- 根の合法手を一度生成して再利用する。
- 初回反復が途中で止まった場合、完全に評価できた根の手のうち最良の手を返す。
  完成深さは0のままとし、評価済み根の手数・合法手数・試行深さを別に記録する。
- arenaには未評価fallback回数と根の探索率を追加する。

固定深さ1・2の値を独立した全幅探索と比較し、一致をテスト。
評価符号、持ち駒の加減算、千日手履歴、盤面復元、部分反復での選択もテストした。
既存の二歩・打ち歩詰め・行き所のない駒・王手回避・成り・詰み・連続王手の千日手テストも維持する。
今回の診断で、これらのルールや持ち駒評価・符号の誤りは見つかっていない。
入玉と公式CSA時計が未対応である点は、以前からの制限として残る。

## 教師125局面に減った理由の診断

v1は2秒または4096ノードの予算内に2手探索を完了できなければ、その教師ラベルを除外する。
したがって、同じseedでもCPU速度・負荷によって採用局面数が変わる。
ラベル不足を無条件に「サンプリングのバグ」とは断定できない。

Cloudに保存したv1の同じ10ゲームに対し、局面生成seed・設定・2秒・4096ノード・教師深さ2を維持して再診断した。
v1の採用ラベルは合計18件、検索処理v2では38件だった。v1で採用された18件の局面は全て再び含まれた。
合法手生成のオーバーヘッドが、ラベルの完成数にも影響していることを確認した。
Kaggleで125件に減った内訳の断定には、実際のconfig・data-manifest・data-progressを追加照合する。
