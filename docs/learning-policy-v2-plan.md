# 方策・価値モデル v2：教師あり学習の再実験

2026-10-30 JST。前回のGPU線形モデルは、修正版探索の128局でも学習前への改善を確認できなかった。
今回は教師と表現を変更する。初回の工程確認と混同せず、新しい実験として扱う。
学習GPUは親側で実行し、最大1時間以内。準備段階では追加GPUを起動しない。

## 変更理由とモデル

前回は教師125件、train 97件、1141特徴だった。浅い材料評価を線形補正しても、指し手の相互作用を十分に表現できなかった。
今回はCPUで高速に探索できるNNUE教師を使い、合法手の方策と局面の価値を同時に学ぶ。
教師の重みや構造を学生へ移植する方式ではなく、新規初期化した小型CNNへの教師あり学習である。強化学習ではない。

- 入力43平面: 手番側・相手側の14駒種、双方7種類の持ち駒、反復回数。
- 手番側を下にする180度回転で正規化。盤上駒と持ち駒、評価符号のテストを行う。
- 32チャネル・残差ブロック2個。方策は27方向/駒打ち種×81マス、価値はtanh出力1個。
- 方策は合法手だけにマスクし、教師の最善手とのcross entropyを計算。
- 価値の教師は手番側の`tanh(cp/600)`、詰み評価は符号に応じて±1。
  校正済みの実勝率だとは主張しない。
- 損失は方策CE＋価値MSE。AdamW、学習率0.001、weight decay 0.01、最大80epoch、batch128、seed314160。
- モデル選択はvalidationの上記合計損失のみ。testは最後の選択モデルでのみ報告し、対局から選び直さない。
- 学習前後とも同一のPUCT、探索係数1.5、最大128シミュレーション、同じ持ち時間。
  反復深化とシミュレーション深さ・ノードは異なる意味なので、同じ指標として比較しない。

## CPU教師生成と重複対策

- 本実験の予定: seed20261104、512ゲーム、各16採取時点、最大160手。教師32768ノード、軌跡用2048ノード。
- 初めの12手はseed固定の合法手で多様化し、その後は8%の合法手選択と教師の手を混ぜる。
  軌跡の勝敗をそのまま棋力の証拠にはしない。
- USIへ局面だけでなく履歴も渡す。各ゲームの初めにisreadyで教師の探索状態を初期化する。
- 教師の手・符号付き評価・深さ・実ノード・実時間、採取時点・終局・除外理由を保存する。
  前回のように「なぜ減ったか」が分からない出力にしない。
- 以前のGPU及びCPUのv1入力と、旧特徴量の正規化/鏡像キーで照合して除外する。
- 今回の79局面の機能確認用データも、盤面・持ち駒の回転/鏡像キーで照合して除外する。
- 新データはゲーム単位でtrain/validation/testに分割。手番回転・鏡像で等価な盤面と持ち駒は全splitを通じて1件にする。
  反復回数が違うだけの同じ盤面もまとめる。読込時にも重複・splitのgame_id交差を検査する。
- 学習・validation・testのどれとも重ならない新規開始局面を最終対局に使う。
- GPU用はtrain 2000件以上、validation/test各200件以上を必須にする。足りなければGPUを起動しない。
- 生成・manifest・NPZ・チェックサムはCPU工程。NPZは`allow_pickle=False`で読む。

## 少量CPU試験の実績

開発途中の機能確認として、20ゲーム・各4採取時点・最大64手、教師8192ノード・軌跡1024ノードで試した。
約8.44秒で79局面（train63 / validation8 / test8）を生成し、3epoch・6 optimizer更新のCPU学習が終了した。
GPU更新は0。JSONモデルでCPU推論と合法手選択まで動いた。
8局・16手上限の機能確認も不正手・時間負け・例外0で完了したが、全局が手数上限なので棋力評価に使わない。
開発試験のモデル・局面を本実験の性能選択に使わず、本実験は固定したソースと新しいディレクトリで実行する。

CPU教師の平手初期局面での動作確認:

- 0.05秒指定: 実測約0.05035秒、72,985ノード、合法手`2g2f`。
- 0.10秒指定: 実測約0.09941秒、146,764ノード、合法手`2g2f`。

これは起動・時間指定・教師の探索が動くことの確認で、Eloや大会順位を推測する材料ではない。

## 学習・評価の実行分離と停止

1. CPUでデータ生成・来歴検査。生成上限1800秒、ゲームごとに保存。
2. 非公開の`policy-v2-gpu-inputs.zip`へNPZとmanifestだけを保存し、各ファイルとZIP全体のSHAを固定する。
3. コードをコミットしてからNotebookのソースバンドルを生成する。
   同梱した全`.py`と生成元commitを照合し、別ディレクトリでオフラインimportとソースSHAの一致を確認する。
4. 親側で無料GPU残量をUI確認。非公開・Internet OFFで学習Notebookを実行。
   PyTorch 2.11.0と既存CUDAを再利用し、インストール・更新を行わない。
5. 学習は3300秒、全体監視3500秒＋終了猶予15秒。最大でも1時間以内の処理上限とする。
   実験用のT4×2割当なら、約2 GPU時間弱に加えて余裕のある無料残量を要求する。
6. 保存後すぐセッションOFF。教師生成・対局はGPU Notebookで行わない。
7. 保存済みモデルをCPUへ戻し、新規対局を実行する。JSONの実重みSHAとファイルSHAを分けて確認する。

epochごとにモデル・optimizerをcheckpointへ保存し、停止はbatch境界で受ける。
途中epochで止まった場合は最後の完全保存epochから同じshuffle順で再開し、消費時間をリセットしない。
CUDA更新は実デバイスで完了を同期してから記録する。保存ファイルの存在だけでGPU学習成功とはしない。
ソース・データ・設定・チェックポイントの不一致、非有限値、CUDA不在、無料残量不足は停止条件。
追加の権限、課金、外部同意、未承認バイナリが必要な場合は該当操作を止めて報告する。

## 最終CPU対局の事前計画

開始局面seed20261106、32開始局面×先後2局。次の4比較で合計256局を予定する。
8局の機能確認に使ったseed20261105は本評価に使わない。

- 学習後対学習前（同一CNN・同一PUCT）。
- 学習後対固定材料評価（修正版alpha-beta）。
- 学習後対固定NNUE教師。
- 学習前対同じ固定NNUE教師。

全員1手0.10秒、1CPUスレッド。学生PUCTは128シミュレーション、材料評価は6000ノード。
NNUEは同じmovetime指定で動かし、棋力を合わせるための意図的な深さ制限・弱化はしない。
最大384手、0.5秒超は時間負け。初期化とモデルロードを各手の思考時間に混ぜず、実思考時間も記録する。
評価上限3600 CPU壁時計秒、2並列。途中ならpausedとし、全比較完了前に成功とはしない。

先後ペア単位のbootstrap 95%区間と保守的Hoeffding境界、不正手・異常終了・時間負け・千日手・打切率を報告する。
以前の成功基準（30ペア以上、保守的下限>50%、異常0、手数打切20%以下）は維持する。
旧ベースラインへの改善と、強い教師を超えたかどうかは別のフラグで報告し、強い相手への敗北も隠さない。
入玉宣言は未裁定なので、教師が宣言勝ちを返した場合は例外として記録し、勝敗を捏造しない。
公式CSA時計・大会接続・出場準備が完了したという意味ではない。
